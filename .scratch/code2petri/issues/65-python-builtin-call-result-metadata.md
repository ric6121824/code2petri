# 65: Inspect Python built-in call results and import aliases

**What to build:** Users can inspect trustworthy result types for supported Python built-in calls even when there is no indexed project-source callee definition. The viewer distinguishes each contained call from its enclosing function's returned expression, explains Unknown with a specific reason, and preserves the evidence through supported inference, folding, and offline saved sessions. Simple explicit import aliases retain the same built-in contract.

**Blocked by:** None (can start immediately).

**Status:** ready-for-agent

- [ ] Support a documented static normal-result catalog for range→range, len→int, str→str, int→int, float→float, bool→bool, list→list, tuple→tuple, dict→dict, and set→set. Range denotes Python's immutable integer sequence. Claims describe the result if a call completes normally, not guaranteed execution, argument validity, inferred element types, or evaluated values. Never execute/import the analyzed application or invoke its callables to obtain evidence.
- [ ] Recognize unshadowed bare catalog names, explicit imports from builtins with optional imported-name aliases, and qualified calls through an explicit builtins module import with optional module aliases. Derive identity from supported lexical bindings and actual import targets, not alias spelling. Rebinding, parameter/local/global shadowing, conflicting imports/project definitions, wildcard imports, writes to catalog attributes through a recognized builtins module binding, unsupported writes/control flow, or dynamic uncertainty must not inherit a catalog contract. Assignment-created callable aliases and alias chains are deferred.
- [ ] Capture independent Call Result Metadata for each call from original source expression/location and owning function/statement identity. Retain repeated, nested, and multiple calls on the same transition without last-call overwrite. Store result type/state, canonical built-in identity where recognized, and static-contract provenance or a specific unknown reason separately from labels and enclosing Function Return Metadata. Field names and storage factoring remain implementation choices.
- [ ] In the existing sidebar, show the enclosing return-expression/function evidence and contained-call results separately. The create_board example displays an enclosing list result and a contained range call's range result with distinct expression/location/provenance. Root information continues to describe the root function; Global Scope stays Not applicable. A return statement containing a call must not be presented as though the statement itself were that callee.
- [ ] Unsupported or uncertain calls display Unknown with an informative reason such as unavailable contract, unsupported built-in/alias form, or shadowed/uncertain binding. Distinguish absent metadata in an older snapshot from an analyzed unknown result. Do not borrow another function's record, a known inner call's result, the enclosing expression's type, or a written annotation as verified call evidence. Existing declared custom types remain visible independently.
- [ ] Reuse recognized built-in contracts in directly returned calls and the existing supported expressions, assignments, reassignments, and copies. A direct returned range call and a returned local assigned that call can infer range. Keep known outer and unknown inner calls independent, and keep unknown outer calls unknown despite known inner calls. Preserve conservative invalidation, incomplete coverage, declaration/inference distinctions, and async/generator result roles; arbitrary project-callee propagation is outside this slice.
- [ ] Known contract evidence remains independent of project-source Call Site resolution. It must not set source resolution to true, create a fake target source file or function definition, make a built-in call expandable, or change existing resolution color/behavior. Preserve constructor-only Variable Bindings and existing call resolution; the new binding analysis serves result evidence only.
- [ ] Retain optional metadata and correct occurrence associations in generated HTML, public net JSON, cloned/composite nets, and version-1 Fold State Snapshots. Renaming, supported folding, and Component-Local Unfold preserve/restore evidence without fabricating a contract for arbitrary multi-function components. Save/open inspection is offline and uses stored evidence, without reevaluating expression strings, rereading source, or applying a new catalog to old labels.
- [ ] Validate recognized new metadata structures, states/reasons, and associations before replacing active session state; malformed data preserves the current graph/document/viewport. Old snapshots remain compatible and explain missing evidence honestly. Keep detached capture and compact history, with shared records/references rather than repeated whole catalogs or full source/AST payloads at nested restoration levels.
- [ ] Verify the complete behavior through the existing source-to-generated-viewer/session seam. Include all ten contracts, bare/imported/qualified/module-alias forms, alias rebinding and shadowing, unsupported forms/custom types, multiple/repeated/nested calls, the create_board list/range distinction, direct returns/locals, known outer/unknown inner and the reverse, incomplete coverage, and specific unknown reasons. Inspect production panel output and public metadata, then save/open/continue-fold/local-unfold using self-contained fixtures; cover active-document replacement, old/malformed snapshots, and compactness. No application execution or private-helper/string-pattern assertions substitute for observable evidence.
- [ ] Keep graph identities/topology, tokens, fold eligibility/results, component history/names, Transition Weight, Component Penalty, Structuredness Metric, Project Title, sidebar visibility, and viewport behavior unchanged. Other libraries/languages, assignment aliases, and custom-type/type-alias resolution are To-do roadmap items rather than blockers or hidden scope in this ticket.

## Context

This is a new Phase 2.10 follow-up to the implemented return-metadata foundation and list-expression inference. An unavailable project-source definition and an unavailable result contract are different conditions. Python built-in contracts can provide static evidence when binding identity is established; arbitrary unresolved names cannot. The present transition-level association can represent several contained calls, so independent per-call records are required for honest display.

“Simple import alias” means an explicit imported built-in name or module bound under another name, with that target still established at the call. It does not mean guessing a programmer-defined data type from an alias. Broader custom-type and alias evidence is deferred in the grand plan.
